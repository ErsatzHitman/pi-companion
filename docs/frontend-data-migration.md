# Frontend Data Migration — Phase 0 Decision (plan §5.3)

**Date:** 2026-08-31
**Worktree:** `D:\pi-companion\.pi\worktrees\phase0-three-round-v2-mthg2mtf-e`
**Reference:** plan §5.3 (migration-only exception), §5.1–§5.2 exclusion boundary, §12.5 offline behavior, §15.3 Android distribution, §17 rollback

## 1. Purpose

Decide, before any workspace is wired (T12) or any native build is produced (T16/T17), which — if any — legacy client-only data held by a previously installed "Paseo / Pi Companion" build must be exported and imported into the new Pi Companion greenfield repository, and which data is safe to discard or re-create by re-pairing.

Per plan §5.3 this is the **only** allowed change to legacy frontend code: a small, isolated export utility may be added **inside the legacy checkout** (never in this repository). If there is no valuable legacy client data, skip the utility and re-pair the new applications.

The replica cache does not need migration because the daemon is authoritative. Push tokens may be re-registered.

The export format must be versioned JSON and must not include daemon passwords or private relay keys unless encrypted.

**Overall Phase 0 decision: RESET / RE-PAIR — no export utility is created.**

Justification:

- No authored, non-recreatable value lives in any of the four §5.3 client-only classes beyond what the daemon already persists (sessions, files, transcript history in `$PASEO_HOME` are daemon-owned and untouched by frontend rebuild — plan §17 rollback notes they remain runnable against the same `$PASEO_HOME`).
- Creating an export utility would be the only edit to legacy frontend code allowed by §5.3, and it would require versioned-JSON + encrypted secret handling with audit surface. Cost outweighs value for a greenfield fresh install.
- T42 (Phase 7, group G11, depends on T10) will execute **exactly this decision**: no versioned-JSON import path is implemented; instead the fresh flow (QR pairing → empty draft/outbox) is verified against this doc. If a future install discovers valuable legacy drafts on a physical device, the export utility can still be authored inside the legacy checkout per §5.3 at that time — nothing in this decision forecloses it. Any such utility would then be imported via T42's versioned-JSON path (tested with encrypted-secrets redaction per §16).

## 3. What Happens in T42 (execution of this decision)

- **No import:** T42 will not add an import path or schema migration for legacy drafts/hosts/attachments.
- **Verification:** T42 will confirm (on web and Android):
  - Fresh pairing succeeds (direct + relay) and the host list starts empty then populates correctly.
  - Drafts survive simulated restart via the _new_ storage interface (frontend-core offline tests), but legacy drafts are not loaded.
  - Outbox refuses automatic resend when idempotency is unverified (§12.5 safe semantics) — tested without legacy outbox.
  - Diagnostics redaction tests pass (no secrets in exports — §16, §14.2 synthetic fixture rule).
- **If later needed:** the export format would be versioned JSON (example envelope below) and must satisfy plan §5.3 secrecy: encrypted bearer/relay secrets or omitted entirely. The utility would live in the legacy checkout (`D:\paseo` or a Paseo fork), never in `D:\pi-companion`. T42 would then add an import test matching that envelope.
